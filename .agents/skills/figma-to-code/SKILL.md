# Figma 디자인을 코드로 구현

Figma 접근과 구현을 분리한다. 새 Figma 조회가 필요하면 먼저 AGENTS.md의 단계별 스킬 표에서 Figma 조회에 해당하는 스킬을 적용하고, 이 스킬은 확보한 REST 구조·이미지 또는 MCP 디자인 맥락을 바탕으로 화면을 하나씩 구현하고 검증한다.

구현 전에 적용되는 저장소 지침, 기능 PRD, 디자인 시스템과 기존 공통 컴포넌트를 확인한다. 프로젝트 규칙이 Figma와 다르면 조용히 한쪽을 택하지 말고 차이와 영향을 먼저 알린다.

## 1. 화면 목록과 순서

REST로 섹션 JSON을 받은 경우에는 바로 아래의 보이는 `FRAME`을 추출해 노드 ID, 프레임 이름, 크기, 관련 PRD 화면 번호를 정리한다.

```bash
jq -r '.nodes[].document.children[] | select(.type=="FRAME" and .visible!=false) | "\(.id)\t\(.name)\t\(.absoluteBoundingBox.width)x\(.absoluteBoundingBox.height)"' <파일>
```

MCP로 프레임 하나를 읽은 경우에는 해당 노드를 작업 대상 하나로 두고 MCP 응답의 이름·크기·컴포넌트·변수 정보를 사용한다. 같은 목록을 만들기 위해 REST로 다시 조회하지 않는다.

- 같은 화면의 빈 상태·오류·토스트·모달은 한 화면 작업으로 묶는다.
- 목록 → 작성 → 상세처럼 실제 의존 순서로 정한다.
- PRD와 프레임이 다르면 문구·동작·이동 방향을 구현 전에 알린다. 임의로 어느 한쪽을 확정하지 않는다.

## 2. 화면별 구현

화면 하나를 구현하고 검증한 뒤 다음 화면으로 간다. Figma에는 다시 요청하지 않고 처음 확보한 REST 캐시 또는 MCP 응답을 재사용한다.

### 수치와 문구 읽기

REST JSON이 있으면 이 스킬 폴더의 `scripts/summarize-node.jq`로 프레임의 레이아웃·색·문구를 요약한다. 숨김 레이어는 구현 근거에서 제외한다.

```bash
jq -r --arg id '<프레임 노드 ID>' -f <figma-to-code 스킬 경로>/scripts/summarize-node.jq "docs/prd/<PRD 폴더>/figma/<파일>.json" | grep -v HIDDEN
```

MCP로 읽었다면 같은 노드의 기존 MCP 응답에서 수치·문구·연결 정보를 사용한다. 요약 JSON을 만들기 위해 REST를 추가 호출하지 않는다.

### 구현

- 현재 프로젝트의 디자인 토큰·공통 컴포넌트·아이콘 체계를 먼저 찾아 재사용한다.
- Figma의 변수 이름이 없거나 프로젝트 토큰 이름과 다르면 실제 값과 의미를 대조해 대응하는 토큰을 찾는다.
- 여러 화면이 공유하는 상태 배지·날짜 형식 같은 도메인 표현은 프로젝트 구조에 맞는 공용 위치에 둔다.
- 아직 없는 화면으로 이동하는 동작은 실제 기능처럼 꾸미지 말고 미구현 상태임을 명시한다.
- 원본에 없는 동작·문구·상태를 임의로 추가하지 않는다.

## 3. Figma 수치 검증

**화면 크기·간격·높이·너비·줄 높이는 Figma 수치가 기준이다. 1~2px 차이도 무시하지 않고 원인을 찾아 맞춘다.**

- Figma 스트로크는 박스 안쪽에 그려져 크기에 더해지지 않는다. CSS `border` 때문에 외곽 크기가 늘어나면 `inset shadow`나 `ring-inset`처럼 크기를 바꾸지 않는 방식으로 구현한다.
- 디자인 토큰 값과 Figma 수치가 다르면 Figma 수치를 사용하고, 토큰을 쓰지 않은 이유를 코드나 결과 보고에 남긴다.
- Figma 프레임과 같은 viewport에서 별도의 Playwright 브라우저로 실제 화면을 연다. 사용자의 개인 브라우저나 기존 세션은 사용하지 않는다.
- Playwright `boundingBox`로 주요 컨테이너·행·버튼·배지의 실제 크기와 위치를 측정해 Figma 값과 비교한다.
- 글자 내용이나 폰트 렌더링에 따라 자연스럽게 정해지는 폭만 ±1px를 허용한다. 고정 크기와 간격에는 적용하지 않는다.
- 차이가 남으면 원인과 영향을 기록한다. 단순히 "무시해도 됨"으로 처리하지 않는다.

## 4. 화면 상태 검증과 보고

- 로딩·오류·빈 상태·경계 상황을 Playwright로 재현한다.
- 구현 내용, 남은 질문, Figma와 끝내 맞추지 못한 항목과 이유를 보고한다.
- 일치한 수치를 전부 표로 나열하지 않는다.
- 커밋은 사용자가 명시적으로 요청할 때만 하며, 해당 프로젝트의 커밋 규칙을 따른다.
- 브라우저 검증이 만든 임시 산출물은 프로젝트 변경과 섞이지 않게 정리한다.

모든 화면이 끝나면 Figma 조회 스킬이 기록한 실제 Figma 요청 횟수도 함께 알린다.
