# tdd-write-test-list

테스트 목록 단계의 절차다. PRD를 테스트 목록으로 바꾼다. 이 단계는 **목록만 만든다.** 테스트 코드나 구현 코드는 작성하지 않는다. 구현은 구현 단계에서 한다.

단계 이름은 AGENTS.md를 따른다.

## 입력과 출력

- 입력: PRD (파일 경로 또는 대화에 붙여 넣은 내용)
- 출력: PRD 폴더의 `test-list.md` (예: `docs/prd/[KD3-636] pass-registration/test-list.md`, 저장소 루트 기준)
  - PRD 폴더는 통합 PRD를 만든 단계가 만든 `docs/prd/[<Jira 티켓 번호>] <소문자 영어 PRD 제목>/`이다. 새로 만들지 않는다. PRD 폴더를 알 수 없으면 사용자에게 묻는다.
  - 같은 PRD의 파일이 이미 있으면 새로 만들지 않고 그 파일을 수정한다. (아래 "기획 변경 시" 참고)

## 전제 조건

PRD의 Open Questions가 모두 해결된 상태를 전제로 한다.

아래 중 하나라도 해당하면 목록을 작성하지 말고 멈춘 뒤, 해당 부분을 PRD 항목 번호와 함께 보고한다.

- PRD에 미해결 Open Question이 있다.
- 요구사항이 모호해서 기대 동작을 하나로 정할 수 없다.
- 요구사항끼리 충돌한다.

## 절차

### 1. PRD → 기능 목록

- PRD의 요구사항 하나를 기능 하나로 만든다.
- 기능은 PRD에 나온 순서대로 적는다.
- 기능마다 PRD의 해당 항목 번호나 제목을 적는다.

### 2. 기능 → 케이스 목록

기능마다 아래 세 종류의 케이스를 나열한다.

- 기본 케이스: 정상 입력에서 기대하는 동작
- 실패 케이스: 잘못된 입력, 권한 없음, 서버 에러 등
- 엣지 케이스: 빈 값, 0, 최대값, 경계 날짜, 중복 등

케이스 작성 규칙

- 케이스 하나는 동작 하나만 다룬다.
- "~하면 ~한다" 형태로, 사용자나 호출하는 쪽에서 보이는 결과를 적는다.
- 내부 구현(함수명, state 이름, 호출 횟수)을 케이스에 쓰지 않는다.

### 3. 케이스별 테스트 수준 정하기

케이스마다 Q1부터 순서대로 확인하고, 처음 "예"가 나오는 곳에서 멈춘다. 결과를 케이스 앞에 `[유닛]`, `[컴포넌트]`, `[E2E]`, `[생략]` 태그로 붙인다.

**Q1. 유닛**: 아래 두 조건을 모두 만족하는가?

- (a) 화면 없이, 함수나 훅에 입력을 넣고 반환값만 보면 결과를 확인할 수 있다.
- (b) 입력을 그대로 넘기지 않고 계산, 변환, 판단(분기)해서 다른 값을 만든다.

흔한 예: 금액·수량·할인 계산, 날짜·기간 계산, 권한 분기, 서버 응답을 화면용 데이터로 변환, 입력값 검증, 정렬·필터·그룹핑

**Q2. 컴포넌트**: 사용자 조작이나 상태에 따라 화면이 달라지는가?

흔한 예: 클릭·입력으로 화면이 바뀜, 로딩·에러·빈 상태 표시, 조건에 따른 요소 노출, 폼 검증 메시지, 2개 이상 화면에서 쓰는 공통 컴포넌트

- 사용자가 하듯이 조작하고, 화면에 보이는 결과로 확인하도록 케이스를 적는다.

**Q3. E2E**: 여러 페이지를 넘나들고, 실패하면 핵심 업무(로그인, 가입, 결제, 예약 등)가 막히는가?

- E2E 케이스는 PRD 하나에 최대 3개까지만 둔다. 더 필요해 보이면 멈추고 보고한다.

**Q4. 생략**: 위에 하나도 해당하지 않는다.

흔한 예: 로직 없이 보여 주기만 하는 화면, 스타일·레이아웃, 정적 문구

- 생략한 케이스도 기능 안에 함께 적는다. 체크박스 없이 `- [생략] <케이스> — 사유: <한 줄>`로 적는다.

**동률 규칙**: 여러 수준에 해당하면 더 빠른 쪽을 고른다. 유닛 > 컴포넌트 > E2E

**예외 규칙**: Q4로 분류했지만 동작이 맞는지 불안하면 테스트 수준을 지정하고, 케이스 끝에 `— 예외 사유: <한 줄>`을 붙인다.

### 4. 기존 테스트 확인

생략을 제외한 케이스마다 같은 동작을 검사하는 테스트가 이미 있는지 확인한다.

- 검색 대상: 테스트 파일(`*.test.*`, `*.spec.*`, E2E 테스트 폴더)의 `describe`, `test`, `it` 이름
- 검색어: 기능 이름, 케이스의 핵심 단어, 관련 컴포넌트·함수 이름

확인 결과에 따라 케이스 끝에 상태를 붙인다. 기존 테스트는 `<파일 경로> > "<테스트 이름>"` 형식으로 적는다.

| 상태 | 뜻 | 사람의 결정 |
|---|---|---|
| 신규 | 같은 동작을 검사하는 테스트가 없다 | 필요 없음 |
| 기존 있음 | 기존 테스트 1개가 이미 같은 동작을 검사한다. 새로 작성하지 않는다 | 필요 없음 |
| 중복 | 기존 테스트 2개 이상이 같은 동작을 검사한다 | `삭제` 또는 `유지` |
| 기존 수정 | 기존 테스트가 있지만 이번 기획으로 기대 동작이 바뀐다 | `승인` 또는 `보류` |

표기 형식

```markdown
- [ ] [수준] <케이스> (신규)
- [x] [수준] <케이스> (기존 있음: <파일> > "<테스트 이름>")
- [x] [수준] <케이스> (중복: <파일 A> > "<테스트 이름>", <파일 B> > "<테스트 이름>")
  - 제안: <삭제할 테스트> 삭제 — <이유>
  - 결정:
- [ ] [수준] <케이스> (기존 수정: <파일> > "<테스트 이름>")
  - 변경: <기존 기대 동작> → <바뀔 기대 동작>
  - 결정:
```

- 중복일 때 남길 테스트는 케이스 문장처럼 동작을 더 명확히 설명하는 쪽, 더 빠른 수준의 쪽을 제안한다.
- `- 결정:` 줄은 비워 둔다. 사람이 파일을 읽고 적는다.
- 구현 단계는 결정이 비어 있는 항목이 하나라도 있으면 시작하지 않는다.
- 기존 테스트를 직접 고치거나 삭제하지 않는다.

### 5. 파일 작성과 보고

- 아래 형식으로 PRD 폴더의 `test-list.md`를 작성한다.
- 작성이 끝나면 **저장한 파일의 절대경로만** 보고한다.
- 사람이 파일을 읽고 확정하기 전에는 구현을 시작하지 않는다.

## 파일 형식

```markdown
# 테스트 목록: <PRD 제목> (PRD 폴더: <PRD 폴더 이름>)

## 기능: <기능 이름> (PRD <항목 번호 또는 제목>)
- [ ] [유닛] <케이스> (신규)
- [생략] <케이스> — 사유: <한 줄>

## 변경 이력
- YYYY-MM-DD: 최초 작성
```

예시

```markdown
## 기능: 쿠폰 적용 (PRD 3.4)
- [ ] [유닛] 정률 쿠폰이면 할인율만큼 뺀 금액을 반환한다 (신규)
- [ ] [유닛] 최소 주문 금액 미만이면 쿠폰을 적용하지 않는다 (기존 수정: src/cart/discount.test.ts > "최소 금액 검사")
  - 변경: 최소 주문 금액 1만 원 → 2만 원
  - 결정:
- [x] [유닛] 할인 후 금액이 0보다 작으면 0을 반환한다 (중복: src/cart/discount.test.ts > "음수 금액 방지", src/cart/total.test.ts > "할인 후 0 미만 처리")
  - 제안: total.test.ts의 테스트 삭제 — 할인 로직은 discount에 있음
  - 결정:
- [ ] [컴포넌트] 쿠폰 버튼을 누르면 쿠폰 모달이 열린다 (신규)
- [ ] [컴포넌트] 유효하지 않은 코드면 에러 메시지가 보인다 (신규)
- [생략] 쿠폰 안내 문구를 표시한다 — 사유: 로직 없이 문구만 보여 줌
```

## 기획 변경 시 (구현 시작 전)

이미 구현이 시작된 기능의 변경은 이 단계가 아니라 구현 단계의 기획 변경 절차를 따른다.

1. 바뀐 PRD가 전제 조건을 만족하는지 확인한다.
2. 기존 PRD 폴더의 `test-list.md`를 연다.
3. 바뀐 PRD와 비교해 기능과 케이스를 추가, 수정, 삭제한다. 3단계(수준)와 4단계(기존 테스트 확인)도 다시 한다.
4. `## 변경 이력`에 날짜, 바뀐 기획, 바뀐 기능을 한 줄로 적는다.
5. 파일의 절대경로만 보고한다.

## 하지 않는 것

- 테스트 코드와 구현 코드를 작성하지 않는다.
- 기존 테스트를 수정하거나 삭제하지 않는다.
- PRD에 없는 기능이나 케이스를 추측해서 추가하지 않는다. 필요해 보이면 멈추고 보고한다.
