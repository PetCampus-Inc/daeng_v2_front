# Figma 스타일 점검

Figma 접근과 점검을 분리한다. 새 Figma 조회가 필요하면 먼저 AGENTS.md의 단계별 스킬 표에서 Figma 조회에 해당하는 스킬을 적용하고, 이 스킬은 확보한 REST 구조·이미지 또는 MCP 디자인 맥락을 이미 구현된 화면과 비교한다.

화면 구현과 차이 수정은 이 스킬이 하지 않는다. 차이를 찾아 보고하고, 고치는 일은 구현을 맡은 쪽이 한다. 저장소 지침, 기능 PRD, 디자인 시스템이 Figma와 다르면 조용히 한쪽을 택하지 말고 차이와 영향을 알린다.

## 1. 점검 대상 정리

REST로 섹션 JSON을 받은 경우에는 바로 아래의 보이는 `FRAME`을 추출해 노드 ID, 프레임 이름, 크기, 관련 PRD 화면 번호를 정리한다.

```bash
jq -r '.nodes[].document.children[] | select(.type=="FRAME" and .visible!=false) | "\(.id)\t\(.name)\t\(.absoluteBoundingBox.width)x\(.absoluteBoundingBox.height)"' <파일>
```

MCP로 프레임 하나를 읽은 경우에는 해당 노드를 점검 대상 하나로 두고 MCP 응답의 이름·크기·컴포넌트·변수 정보를 사용한다. 같은 목록을 만들기 위해 REST로 다시 조회하지 않는다.

- 같은 화면의 빈 상태·오류·토스트·모달은 한 화면 점검으로 묶는다.
- PRD와 프레임이 다르면 문구·동작·이동 방향을 점검 전에 알린다. 임의로 어느 한쪽을 확정하지 않는다.

화면 하나를 점검한 뒤 다음 화면으로 간다. Figma에는 다시 요청하지 않고 처음 확보한 REST 캐시 또는 MCP 응답을 재사용한다.

## 2. 수치와 문구 읽기

REST JSON이 있으면 이 스킬 폴더의 `scripts/summarize-node.jq`로 프레임의 레이아웃·색·문구를 요약한다. 숨김 레이어는 점검 근거에서 제외한다.

```bash
jq -r --arg id '<프레임 노드 ID>' -f <figma-style-check 스킬 경로>/scripts/summarize-node.jq "docs/prd/<PRD 폴더>/figma/<파일>.json" | grep -v HIDDEN
```

MCP로 읽었다면 같은 노드의 기존 MCP 응답에서 수치·문구·연결 정보를 사용한다. 요약 JSON을 만들기 위해 REST를 추가 호출하지 않는다.

## 3. 수치 점검

**화면 크기·간격·높이·너비·줄 높이는 Figma 수치가 기준이다. 1~2px 차이도 무시하지 않고 차이로 기록한다.**

- Figma 스트로크는 박스 안쪽에 그려져 크기에 더해지지 않는다. CSS `border` 때문에 외곽 크기가 늘어났다면 차이로 기록하고, `inset shadow`나 `ring-inset`처럼 크기를 바꾸지 않는 방식을 원인 후보로 적는다.
- Figma 프레임과 같은 viewport에서 별도의 Playwright 브라우저로 실제 화면을 연다. 사용자의 개인 브라우저나 기존 세션은 사용하지 않는다.
- Playwright `boundingBox`로 주요 컨테이너·행·버튼·배지의 실제 크기와 위치를 측정해 Figma 값과 비교한다.
- 글자 내용이나 폰트 렌더링에 따라 자연스럽게 정해지는 폭만 ±1px를 허용한다. 고정 크기와 간격에는 적용하지 않는다.
- 차이마다 원인과 영향을 기록한다. 단순히 "무시해도 됨"으로 처리하지 않는다.

## 4. 디자인 시스템 사용 점검

AGENTS.md의 컨벤션 표에 스타일·디자인 시스템 문서가 있으면 그 규칙을 기준으로 한다.

- 색·글자·간격·반지름이 디자인 토큰으로, 버튼·입력·아이콘이 공통 컴포넌트와 아이콘으로 구현됐는지 확인한다. 직접 쓴 값이 있으면 위치를 기록한다.
- Figma의 변수 이름이 없거나 프로젝트 토큰 이름과 다르면 실제 값과 의미를 대조해 대응하는 토큰이 있는지 확인한다.
- 토큰 값과 Figma 수치가 다르면 Figma 수치가 기준이다. 토큰을 쓰지 않은 이유가 코드나 보고에 있는지 확인하고, 없으면 차이로 기록한다.

## 5. 문구와 상태 점검

- Figma의 문구·상태(활성·비활성·선택·오류 등)가 구현에 빠짐없이 들어갔는지 확인한다.
- 원본에 없는 동작·문구·상태가 임의로 추가되지 않았는지 확인한다.
- 아직 없는 화면으로 이동하는 동작이 실제 기능처럼 꾸며져 있지 않은지 확인한다.

## 6. 반응형 점검

수치 비교는 Figma 프레임 너비에서만 한다. 그 외의 너비에서는 Figma 수치가 없으므로 깨짐이 없는지만 본다.

- Figma 프레임 너비와 작은 모바일 너비(360px) 두 곳에서 화면을 연다.
- 글자 잘림, 요소 겹침, 가로 스크롤, 화면 밖으로 나간 버튼·입력이 있는지 확인한다.
- 긴 이름·긴 문구는 Figma나 PRD에 말줄임·줄바꿈 규칙이 있으면 그대로 구현됐는지 확인한다.
- 깨짐이 있으면 너비, 위치, 증상을 기록한다.

## 7. 화면 상태 점검

- 로딩·오류·빈 상태·경계 상황을 Playwright로 재현해 Figma와 PRD대로 보이는지 확인한다.
- 브라우저 점검이 만든 임시 산출물은 프로젝트 변경과 섞이지 않게 정리한다.

## 8. 보고

- 차이 목록을 보고한다. 항목마다 위치, Figma 값, 실제 값, 원인 후보를 적는다.
- 일치한 수치를 전부 표로 나열하지 않는다. 남은 질문과 Figma와 PRD가 다른 부분도 함께 알린다.
- 코드·테스트를 고치지 않고 커밋하지 않는다.
- 모든 화면이 끝나면 Figma 조회 스킬이 기록한 실제 Figma 요청 횟수도 함께 알린다.
