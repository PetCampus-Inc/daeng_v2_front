# tdd-apply-review

리뷰 반영 단계의 절차다. 한 번 실행에 리뷰 코멘트 한 라운드를 반영한다. 리뷰가 여러 번 오면 라운드마다 다시 실행한다.

단계 이름은 AGENTS.md를, 커밋 규칙과 항상 적용되는 규칙(테스트 보호, 멈춤 조건, 결과 보고)은 `docs/policy/tdd.md`를 따른다.

## 입력

- 현재 브랜치의 PR과 아직 반영하지 않은 리뷰 코멘트
- `docs/prd/[<Jira 티켓 번호>] <소문자 영어 PRD 제목>/test-list.md` (저장소 루트 기준)
- PR이나 테스트 목록이 없으면 멈추고 보고한다.

## 1단계. 코멘트 모으기

- 이번 라운드에서 반영할 리뷰 코멘트를 모두 모은다. 이미 해결된 코멘트는 제외한다.
- 커밋하지 않은 변경이 있으면 시작하지 않고 보고한다.

## 2단계. 코멘트 분류와 처리

코멘트마다 아래 네 가지 중 하나로 분류해 처리한다.

| 분류 | 예 | 처리 |
|---|---|---|
| 코드 정리 | 이름 변경, 함수 분리, 중복 제거 | 동작을 바꾸지 않고 고친 뒤 테스트 통과를 확인하고 `refactor:`로 커밋한다 |
| 버그 | 케이스대로 동작하지 않음 | 구현 단계의 루프로 해당 케이스를 다시 처리한다. 케이스를 놓친 테스트가 있었다면 멈추고 보고한다 |
| 기획 변경 | 동작 변경, 케이스 추가·삭제 | 구현 단계의 기획 변경 절차를 따른다 |
| 반영하지 않음 | 질문, 의견, 다른 작업 범위 | 코드를 바꾸지 않는다 |

- 어느 분류인지 판단이 어려우면 멈추고 묻는다.
- 리뷰어가 테스트 수정을 요청한 경우도 기획 변경으로 보고 기획 변경 절차를 따른다. 테스트 목록에 기록하고 사람의 결정을 받은 뒤 고친다.

## 3단계. 확인과 푸시

1. 유닛·컴포넌트 테스트 전체, E2E 테스트 전체, 린터와 타입 검사를 실행한다. 프로젝트에 E2E 실행 스크립트가 있으면 그것을 쓴다.
2. 실패하면 구현을 고친다. 테스트가 잘못됐다고 판단되면 고치지 말고 멈춘 뒤 보고한다.
3. 테스트 목록이 바뀌었으면 PR 설명을 테스트 목록에 맞게 갱신한다.
4. 푸시한다.

## 4단계. 답글 초안 작성

코멘트마다 답글 초안을 작성해 보고한다. 사람이 초안을 확인하고 직접 답글을 단다.

```markdown
### <코멘트 요약 한 줄> (<파일:줄> 또는 코멘트 링크)
> <답글 초안>
```

- 무엇을 어떻게 바꿨는지, 혹은 반영하지 않은 이유는 무엇인지 짧고 구체적으로 쓴다.

## 하지 않는 것

- 리뷰 코멘트에 답글을 직접 달거나 코멘트를 해결 처리하지 않는다. 초안만 쓴다.
- 승인, 머지를 하지 않는다.
- 테스트 목록을 삭제하지 않는다. 마무리 단계에서 한다.
- 실패 중인 테스트를 통과시키려고 테스트를 고치지 않는다.
