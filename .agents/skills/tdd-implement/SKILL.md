# tdd-implement

구현 단계의 절차다. 확정된 테스트 목록을 따라 TDD로 구현한다.

단계 이름은 AGENTS.md를, 테스트 작성·커밋 규칙과 항상 적용되는 규칙(테스트 보호, 멈춤 조건, 결과 보고)은 `docs/policy/tdd.md`를 따른다.

## 입력

- `docs/prd/[<Jira 티켓 번호>] <소문자 영어 PRD 제목>/test-list.md` (저장소 루트 기준)
- 파일이 없으면 멈추고, 테스트 목록 단계를 먼저 진행해야 한다고 보고한다.

## 시작 전 확인

테스트 목록에 내용이 비어 있는 `- 결정:` 줄이 하나라도 있으면 구현을 시작하지 않는다. 파일의 절대경로와 해당 케이스를 보고하고 멈춘다.

## 1단계. 결정 처리

기능 구현에 들어가기 전에 "중복" 결정을 먼저 처리한다.

| 상태 | 결정 | 처리 |
|---|---|---|
| 중복 | 삭제 | 제안된 테스트를 삭제하고, 남은 테스트가 통과하는지 확인한 뒤 `refactor: 중복 테스트 삭제 (<케이스>)`로 커밋한다 |
| 중복 | 유지 | 아무것도 하지 않는다 |
| 기존 수정 | 승인 | 기능 루프에서 신규 케이스와 함께 처리한다 (2단계) |
| 기존 수정 | 보류 | 구현하지 않고 체크하지 않는다. 완료 보고에 포함한다 |

## 2단계. 기능 루프

테스트 목록의 기능을 위에서부터 하나씩 처리한다.

### 2-1. 처리할 케이스 고르기

- 대상: 체크되지 않은 `(신규)` 케이스, 결정이 `승인`인 `(기존 수정)` 케이스
- 제외: `[생략]`, 이미 체크된 케이스, `보류` 케이스
- 순서: `[유닛]` → `[컴포넌트]` → `[E2E]`
- `[유닛]`, `[컴포넌트]`는 2-2 ~ 2-6을 따른다. `[E2E]`는 2-7을 따른다.

### 2-2. 진행 방식 정하기

기본은 **한 번에**다. 아래 중 하나라도 해당하면 **하나씩**으로 진행한다.

- 날짜·시간 경계를 다룬다. (월말, 윤년, 일할계산, 타임존)
- 둘 이상의 조건이 조합되어 결과가 달라진다. (예: 회원 등급 × 쿠폰 종류)
- 처리할 유닛·컴포넌트 케이스가 6개 이상이다.

| | 한 번에 | 하나씩 |
|---|---|---|
| 테스트 작성 | 기능의 대상 케이스 테스트를 모두 먼저 작성한다 | 케이스 하나의 테스트만 작성한다. 다음 케이스의 테스트는 미리 작성하지 않는다 |
| 구현 | 모든 테스트가 통과하도록 한 번에 구현한다 | 그 케이스만 통과하도록 구현한다 |
| 반복 | 기능당 1회 | 케이스마다 2-3 ~ 2-6을 반복한다 |

### 2-3. 테스트 작성

- `describe`는 기능 이름, `test`는 케이스 문장을 그대로 쓴다. 태그와 상태 표시는 뺀다.
  ```js
  describe('쿠폰 적용', () => {
    test('정률 쿠폰이면 할인율만큼 뺀 금액을 반환한다', () => { /* ... */ });
  });
  ```
- 테스트 코드는 케이스 문장이 정한 기대 동작을 정확히 검사해야 한다. 가능하면 구체적인 값으로 검사한다.
- 테스트 파일 위치와 이름은 프로젝트의 기존 관례를 따른다. 관련 테스트 파일이 있으면 그 파일에 추가한다.
- `[컴포넌트]` 테스트는 사용자가 하듯이 조작하고 화면에 보이는 결과로 확인한다. 내부 state나 함수 호출 여부를 검사하지 않는다.
- `(기존 수정)` 케이스는 새 테스트를 만들지 않고 적힌 기존 테스트의 기대값을 `변경:`에 맞게 수정한다. 테스트 이름도 케이스 문장으로 바꾼다. 사람이 승인한 수정이다.

### 2-4. Red: 실패 확인

`vitest --changed --run`을 실행한다.

- 작성한 테스트가 실패하는지, 실패 이유가 "기능이 없어서" 또는 "기대값과 달라서"인지 확인한다.
- 오타, import 에러, 설정 오류로 실패하면 테스트 코드를 고치고 다시 실행한다.
- 처음부터 통과하는 테스트가 있으면, 테스트가 케이스의 기대 동작을 실제로 검사하는지 점검한다.
  - 테스트에 문제가 없으면: 이미 다른 코드(앞 케이스의 구현, 기존 코드)가 그 동작을 하고 있는 것이다. 테스트를 남기고 케이스를 체크한 뒤, 같은 기능의 다음 커밋에 포함한다.
  - 테스트가 동작을 제대로 검사하지 못하면(검사문 누락, 느슨한 검사, 비동기 대기 누락 등): 테스트 코드를 고치고 다시 Red를 확인한다.

### 2-5. Green: 최소 구현

- 테스트가 요구하는 만큼만 구현한다. 가짜 구현(상수 반환)은 하지 않고 실제 로직을 작성한다.
- 테스트가 실패하면 구현을 고친다. 테스트를 고치지 않는다.
- `vitest --changed --run`으로 통과를 확인한다.
- 통과하면 테스트 목록에서 해당 케이스를 체크하고, 테스트·구현·목록을 함께 `feat:` 또는 `fix:`로 커밋한다.

### 2-6. Refactor: 정리

- 중복, 이름, 구조에 정리할 것이 있을 때만 한다. 없으면 건너뛴다.
- 동작을 바꾸지 않는다.
- `vitest --changed --run`으로 통과를 확인한 뒤 `refactor:`로 커밋한다.
- 하나씩: 다음 케이스로 2-3부터 반복한다.

### 2-7. E2E 케이스

기능의 유닛·컴포넌트 케이스를 모두 처리한 뒤에 작성한다.

- 2-3의 이름 규칙을 따르고, 사용자가 하듯이 페이지를 이동하고 조작하며 화면에 보이는 결과로 확인한다.
- **실행하지 않는다.** 실행은 PR 생성 단계에서 한다.
- 작성하면 케이스를 체크하고 끝에 `— 미실행`을 붙인 뒤 `feat:`로 커밋한다.
- 기능의 케이스를 모두 처리하면 다음 기능으로 넘어간다.

### 공통

- 구현 중 목록에 없는 케이스가 필요해 보이면 추가하지 말고 멈춘 뒤 보고한다.

## 멈추고 보고할 때의 선택지

`docs/policy/tdd.md`의 멈춤 조건에 해당하면 멈춘다. 실패한 테스트와 함께 아래 선택지를 보고한다.

"한 번에" 진행 중 멈춘 경우

1. 커밋하지 않은 테스트와 구현을 마지막 커밋 상태로 되돌리고 "하나씩"으로 다시 진행한다.
2. 지금 상태에서 사람이 원인을 함께 확인한다.
3. 테스트 목록(기획)을 다시 검토한다.

"하나씩" 진행 중 멈춘 경우

1. 지금 상태에서 사람이 원인을 함께 확인한다.
2. 테스트 목록(기획)을 다시 검토한다.

사람이 선택지를 고르기 전에는 아무것도 되돌리거나 수정하지 않는다.

## 기획 변경 시

구현 중이거나 리뷰 중에 기획이 바뀌면 아래 순서를 따른다. 구현 시작 전의 변경은 테스트 목록 단계의 "기획 변경 시" 절차로 기존 테스트 목록을 수정한다.

1. 진행 중인 작업을 멈춘다. 커밋하지 않은 변경이 있으면 사람에게 남길지 되돌릴지 묻는다.
2. 테스트 목록에서 바뀐 기획에 해당하는 케이스를 파일의 기존 형식(수준 태그, 상태 표기)에 맞춰 수정한다.
   - 이미 구현해서 체크된 케이스의 기대 동작이 바뀌면: 체크를 풀고 `(기존 수정: <파일> > "<테스트 이름>")`, `- 변경:`, 빈 `- 결정:`을 적는다.
   - 새로 생긴 케이스: `(신규)`로 추가한다.
   - 없어진 케이스: 목록에서 지우고, 관련 테스트가 있으면 `- 삭제 제안: <파일> > "<테스트 이름>"`과 빈 `- 결정:`을 해당 기능 끝에 적는다.
3. `## 변경 이력`에 날짜, 바뀐 기획, 바뀐 기능을 한 줄로 적는다.
4. 테스트 목록의 절대경로를 보고하고 멈춘다.
5. 사람이 결정을 적으면 "시작 전 확인"부터 다시 진행한다.
   - `삭제 제안`의 결정이 `삭제`이면 테스트를 삭제하고 남은 테스트 통과를 확인한 뒤 커밋한다.
   - 기획 변경을 반영한 커밋은 메시지 끝에 `(기획 변경)`을 붙인다.

## 완료 보고

모든 기능을 처리하면 아래만 보고한다.

- 테스트 목록의 절대경로
- 처리하지 못한 케이스(보류, 멈춤으로 남은 케이스)가 있으면 그 목록
- 다음은 PR 생성 단계라는 안내

## 하지 않는 것

- 테스트 목록에 없는 케이스를 구현하거나 테스트를 추가하지 않는다.
- 실패 중인 테스트를 통과시키려고 테스트를 고치지 않는다. 결정 없이 테스트를 삭제하지 않는다.
- E2E 테스트를 실행하지 않는다. 유닛·컴포넌트 전체 실행도 하지 않는다. 둘 다 PR 생성 단계에서 한다.
