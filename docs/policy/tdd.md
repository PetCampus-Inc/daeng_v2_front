# TDD 규칙

이 규칙은 모든 구현 작업에 항상 적용한다. 경로는 저장소 루트 기준이다.

## 테스트 작성

- `apps/knockdog`의 컴포넌트 테스트 파일은 첫 줄에 `// @vitest-environment jsdom`을 넣는다. knockdog 프로젝트의 테스트 환경이 `node`라서, 이 줄이 없으면 화면을 그리는 테스트가 실패한다.

## 테스트 보호

- 실패 중인 테스트를 통과시키려고 테스트 코드를 고치지 않는다. 실패하면 구현을 고친다.
- 테스트가 잘못됐다고 판단되면 고치지 말고 멈춘 뒤, 어떤 테스트가 왜 잘못됐는지 보고한다.
- 예외: 테스트를 처음 작성하는 중(Red 확인 전)의 오타, import, 설정 오류는 고칠 수 있다.
- 사람의 결정 없이 테스트를 삭제하지 않는다.

## 커밋할 때의 테스트 기준

- 구현 단계에서 "모든 테스트가 통과"는 실행한 유닛·컴포넌트 테스트 기준이다. E2E는 실행하지 않은 상태로 커밋할 수 있다.

## 커밋

- 모든 테스트가 통과하고 린터·타입 에러가 0일 때만 커밋한다.
- 커밋 하나는 논리적 작업 단위 하나다. 작고 자주 커밋한다.
- 구조 변경과 행동 변경은 커밋을 나눈다.
  - 구조 변경: 동작을 바꾸지 않는 정리 (이름 변경, 함수 추출, 파일 이동) → `refactor:`
  - 행동 변경: 동작이 바뀌는 변경 (기능 추가, 버그 수정) → `feat:` / `fix:`
  - 둘 다 필요하면 구조 변경을 먼저 커밋한다.
- 기획 변경을 반영한 커밋은 메시지 끝에 `(기획 변경)`을 붙인다.

## 테스트 결과 보고

- 실패한 테스트는 이름, 기대값과 실제값, 에러 위치만 보고한다.
- 통과한 테스트는 개수만 보고한다.
- 전체 로그를 그대로 붙이지 않는다.

## 멈추고 사람에게 보고할 때

아래 중 하나라도 해당하면 작업을 멈추고, 상황과 선택지를 보고한 뒤 지시를 기다린다.

- 같은 테스트를 고치려고 2번 수정했는데도 실패한다.
- 테스트 목록에 없는 기능을 추가해야 할 것 같다.
- 테스트를 고치거나 삭제해야만 통과할 것 같다.
- 기획(PRD)과 테스트 목록이 서로 맞지 않는다.
