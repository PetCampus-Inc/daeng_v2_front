# tdd-create-pr

PR 생성 단계의 절차다. 구현 단계에서 만든 변경을 전체 테스트로 확인하고 PR을 만든다.

단계 이름은 AGENTS.md를, 커밋 규칙과 항상 적용되는 규칙(테스트 보호, 멈춤 조건, 결과 보고)은 `docs/policy/tdd.md`를 따른다.

## 입력

- `docs/test-lists/<PRD이름>.md` (저장소 루트 기준)
- 테스트 목록 맨 위에 적힌 PRD
- 프로젝트 PR 템플릿 (`.github/pull_request_template.md` 등)
- 테스트 목록이 없으면 멈추고 보고한다.

## 시작 전 확인

아래 중 하나라도 해당하면 시작하지 않고, 테스트 목록의 절대경로와 해당 케이스를 보고한다.

- 내용이 비어 있는 `- 결정:` 줄이 있다.
- 체크되지 않은 케이스 중 결정이 `보류`가 아닌 것이 있다. (구현 단계가 끝나지 않았다)
- 커밋하지 않은 변경이 있다.

## 1단계. 전체 테스트 실행

- 유닛·컴포넌트 테스트 전체를 실행한다. (`vitest --run`)
- E2E 테스트 전체를 실행한다. 프로젝트에 E2E 실행 스크립트가 있으면 그것을 쓴다.
- 린터와 타입 검사를 실행한다.

### 실패 처리

1. 실패한 테스트가 테스트 목록의 어느 기능·케이스에 해당하는지 찾는다. 목록에 없는 기존 테스트라면 이번 변경이 기존 동작을 깨뜨린 것이다.
2. 구현을 고쳐서 통과시키고 `fix:`로 커밋한다. 테스트는 고치지 않는다.
3. 테스트가 잘못됐다고 판단되면 고치지 말고 멈춘 뒤, 어떤 테스트가 왜 잘못됐는지 보고한다.
4. 고친 뒤 1단계를 처음부터 다시 실행한다.

### 처음 실행한 E2E 점검

테스트 목록에서 `— 미실행`이 붙은 E2E는 실패를 한 번도 본 적이 없는 테스트다.

- 통과하면: 테스트가 케이스의 결과를 실제로 확인하는지 점검한다. 페이지 이동만 하고 결과를 확인하지 않는 등 검사가 부족하면 보고한다.
- 점검이 끝난 E2E는 테스트 목록에서 `— 미실행`을 지운다.

## 2단계. PR 설명 작성

프로젝트 PR 템플릿을 열고, 템플릿의 섹션 구조와 서식(배너 이미지 등)을 그대로 쓴다. 각 섹션의 안내 주석(`<!-- -->`)을 읽고, 아래 내용을 뜻이 맞는 섹션에 넣는다. 안내 주석은 지운다.

| 내용 | 출처 | 넣을 섹션 (템플릿 예: `작업 개요` / `작업 내용` / `논의할 점` / `스크린샷`) |
|---|---|---|
| 이 PR이 해결하는 문제와 요약, PRD 위치·링크 | PRD | 작업 개요 |
| 기획 변경 이력 | 테스트 목록의 `## 변경 이력` | 작업 개요 |
| 구현한 기능과 케이스 | 테스트 목록의 체크된 케이스 | 작업 내용 |
| 테스트 변경 | 삭제한 중복 테스트, 수정한 기존 테스트, 생략한 케이스 | 작업 내용 |
| 리뷰 순서 | 커밋 목록 | 작업 내용 |
| 보류한 케이스 | 결정이 `보류`인 케이스 | 논의할 점 |
| 화면 변경 | — | 스크린샷: `화면 변경이 있으면 사람이 첨부` 라고만 적는다 |

섹션별 작성 형식

```markdown
## 작업 개요
<PRD를 바탕으로 한 두세 문장 요약>
- PRD: <경로 또는 링크>
- 기획 변경 이력
  - <테스트 목록의 변경 이력>

## 작업 내용
- <기능 이름> (PRD <항목>)
  - <케이스>

**테스트 변경**
- 삭제한 중복 테스트: <파일> > "<테스트 이름>"
- 수정한 기존 테스트: <파일> > "<테스트 이름>" — <바뀐 기대 동작>
- 생략한 케이스: <케이스> — <사유>

**리뷰 순서**
- 구조 변경 커밋(`refactor:`): 동작이 바뀌지 않았는지만 확인
- 행동 변경 커밋(`feat:`/`fix:`): 케이스대로 동작하는지 확인

## 논의할 점
- 보류한 케이스: <케이스>

## 스크린샷
화면 변경이 있으면 사람이 첨부
```

- 비어 있는 항목은 `- 없음`으로 적는다.
- 템플릿의 섹션 이름이 다르면 안내 주석의 뜻을 보고 가장 가까운 섹션에 넣는다. 맞는 섹션이 없으면 섹션을 새로 만들지 말고 보고한다.
- 템플릿이 없으면 위 형식을 그대로 쓴다.
- PRD와 테스트 목록에 없는 내용을 추측해서 쓰지 않는다.
- PR 제목은 커밋 규칙과 같은 형식(`feat: ...`)으로 PR 전체를 요약해 제안한다.

## 3단계. PR 만들기

1. PR 제목과 설명 초안을 보고하고 멈춘다.
2. 사람이 확인하면 브랜치를 푸시하고 PR을 만든다.
3. PR URL을 보고한다.

## 하지 않는 것

- 사람의 확인 없이 푸시하거나 PR을 만들지 않는다.
- 리뷰어 지정, 승인, 머지를 하지 않는다.
- 테스트 목록을 삭제하지 않는다. 마무리 단계에서 한다.
- 실패 중인 테스트를 통과시키려고 테스트를 고치지 않는다.
